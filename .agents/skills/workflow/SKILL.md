# Workflow

This file is the workflow's memory, written for the agent that changes it: the current decisions with the user's reasons, the facts they rest on, and where the evidence is. It holds the current state only. When a decision changes, rewrite its line in place with the new reason; git history keeps the old one. A thread that changes the workflow updates this file before it finishes — "i don't need to explain each time my decisions when i change the workflow".

## Install

Run from this deslop worktree after changing its personal native configuration or skills. Read the sources and named targets first. Delete the owned configuration, roles and machine skills, then install their current sources; authentication, sessions and unrelated entries stay untouched. This replaces files, not a running session's loaded instructions.

```bash
set -e
CODEX_TARGET=${CODEX_HOME:-"$HOME/.codex"}
CLAUDE_TARGET=${CLAUDE_CONFIG_DIR:-"$HOME/.claude"}
rm -f "$CODEX_TARGET/config.toml" "$CODEX_TARGET/instructions.md" "$CLAUDE_TARGET/settings.json"
rm -f "$CODEX_TARGET/agents/"{explorer,review,worker}.toml "$CLAUDE_TARGET/agents/"{Explore,general-purpose,pair,review}.md
mkdir -p "$CLAUDE_TARGET/agents"
cp .codex/{config.toml,instructions.md} "$CODEX_TARGET/"
cp .claude/settings.json "$CLAUDE_TARGET/"
cp .claude/agents/pair.md "$CLAUDE_TARGET/agents/"
for TARGET in "$CODEX_TARGET" "$CLAUDE_TARGET"; do
  rm -rf "$TARGET/skills/"{environment,maintenance,workflow-main,workflow-research,workflow-implementation,workflow-test,workflow-review,workflow-browser}
  mkdir -p "$TARGET/skills"
done
cp -R .claude/skills/{environment,maintenance,workflow-main,workflow-research,workflow-implementation,workflow-test,workflow-review,workflow-browser} "$CLAUDE_TARGET/skills/"
for SKILL in environment maintenance workflow-main workflow-research workflow-implementation workflow-test workflow-review workflow-browser; do
  ln -s "$CLAUDE_TARGET/skills/$SKILL" "$CODEX_TARGET/skills/$SKILL"
done
```

Compare installed files with their sources. Engineering/design/testing belong to the public repository installer, not this global workflow; keep their existing global migration copies until every affected repo is locally provisioned. Dual is read-only in this task.

## Objective

- Success includes merge-as-delivered quality, fast useful iterations, and low attention/context-switch cost — "increase my satisfaction ... improving the quality and speed and token efficiency"; "the context switch is already making me go crazy". Remove observed overhead at its source throughout the work, not just prototype setup — "whatever is making you slow must be optimized" (10-03). A shorter response or cheaper model is not an improvement if it hides a failure or needs another correction. Single small evals establish their behaviors, not a satisfaction or speed gain.
- The user works from rough intent in one long thread per feature/worktree, steering when ideas arrive; there is no frozen-ticket planning/build handoff — "requirements aren't clear ... exploration, prototypes, trial and error"; "extremely quick iterations instead of a normal planning and questioning". The agent owns research, trials, reversible technical choices and scheduling, continuing unattended without asking the user to orchestrate.
- Workflow evals and prototype experiments use fresh T3-owned children, not terminal agents or ordinary conversations — “new sessions ... replace ... direct cli invocations ... sidebar full of useless threads” (10-03). Fresh children have used updated installed skills on real tasks; shared provider-process configuration reload and hard native-tool denial remain unproven. Keep one prototype host, use existing-thread reads for relevant evidence, and create top-level conversations only on explicit user request. Child storage is not another user work queue.
- Discovery gets the next useful working example and settles what only the user can know, not what tools or skills can answer. The private Done-when list exists from the first example and tracks current criteria, observations and unresolved questions; it evolves rather than freezing a specification. Final check, review, proof and clean net diff remain required.
- Tokens are saved by improving the workflow (less friction, recurring issues fixed), never by handing the user thinking or work the agent can do — "the token saving should be from us optimizing the workflow, removing friction, fixing recurring issues, ... and not just delegating thinking and work that you can just do yourself to me"; "i feel like the agent still consider me like one of it's agents that can call at each time to delegate thinking and work to".
- Cost is subscription quota per merged PR (Claude Max 20x, Codex 5x): a stronger model that merges in one pass beats a cheaper one that needs follow-ups — "i perfer using astra on high rather than luna low if astra can merge in a single pass".

## How to change the workflow

- The workflow is optimized for the happy path only — "In precisions conversations I added conditionals over some parts of the workflow (e.g. don't commit, just plan, …) but we shouldn't consider them in the workflow": no rule for one-off conditionals, and replays score none of them. The rest of the host is read-only for a thread — "Don't touch dual, in general we should say something to treat the rest of the system as read only when working on a repo".
- T3-only providers: the primary model/harness is selected in the composer, not fixed in configuration — “keep the base configs minimal and generic ... different primary models ... delegation ... independently of the base harness” (10-03). Both native bases select workflow-main for ordinary work or the brief's assigned procedure for a bounded task. One shared main skill owns consistent Orchestrator V2 routing; native agents and terminal agent CLIs remain excluded. Codex image generation is enabled; delegate image work with design, not another tool wrapper. T3 owns agents, workspaces, scheduling and UI. No CLIProxy/auth translation. Earlier Claude quota reservation still applies to execution, not configuration.
- Both providers have minimal native role/skill bootstrap bodies; detailed discovery, questions, output, delivery and the model table have one owner, workflow-main. Specialist procedures stay on demand. The main agent retains taste and first instances regardless of harness; no fixed Claude-main/Codex-worker identity, unused model catalogue or manual slash-command instructions. Configuration does not choose a primary model/effort; T3 does.
- Prompts and config only: no hooks, gates, generators, or scripts — "they seems stupid and overcomplicated, fix the prompts since the models should be good enough already". Hooks and generators were built and removed three times.
- Resolve issues up front instead of adding branches for every case — "the whole workflow need to be optimized around resolving the issues up-front and not having tons of branches to handle every possible case".
- Fix root causes at their source: a rejected rule is edited or deleted where it lives, never countered by a new one — "you should clean up and solve the root cause".
- Change on evidence, with small tests that check exactly what a change needs (a captured request, a few bare prompts, lint over the examples, one targeted replay), never large eval rounds — "prefer smaller tests to check what you need and not big tests that add no value" (10-01, after the 09-30 rounds spent most of a week's quota). No word cap — "i don't want to have a word cap". Happy path everywhere, commands and scripts included, for this one machine — "if something is not in the happy path the agent is smart enough to find a solution anyway"; "i only use this machine".
- Before calling workflow work done, ask whether the data supports the conclusion and whether the objective is met; stopping because the literal instruction ran out is the failure the user saw overnight on 09-30 — "these are a couple of questions that the agent should have asked itself before saying that it finish or stopped".
- Evals never touch a remote: no commits, pushes, remote branches, MRs, or destructive operations from any test run — "this is extremely important since i can't just commit on the repo remote just to do tests". Eval copies have no remote, pushes rewritten to an invalid scheme, and invalid forge tokens.
- dual is read-only for workflow work — "Don't do any change to dual"; it is a source of patterns only.
- Global workflow sources belong to native .claude/.codex roots — “global skills ... .claude ... symlink ... .codex ... remove ... .agents/skills ... only ... repo skills” (10-03). .claude/skills holds canonical global procedures; .codex/skills links to it. .agents/skills holds only repository skills, including this workflow-maintenance memory. The public CLI's ignored engineering/design/testing copies under .claude/skills are native repository views, never global installation inputs. The Install recipe replaces named owned global files/directories and links Codex to the installed Claude skill sources; auth, sessions, unrelated skills and temporary public-skill migration copies stay. Relative Codex instructions resolve beside their config. Dual remains read-only; do not delete migration copies before publication/local provisioning or claim project-version selection.

Select reversible technical choices on observed tradeoffs and the user's standards, not a user architecture election. - Open-ended work is the normal case.
