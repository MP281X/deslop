# Workflow

This file is the workflow's memory, written for the agent that changes it: the current decisions with the user's reasons, the facts they rest on, and where the evidence is. It holds the current state only. When a decision changes, rewrite its line in place with the new reason; git history keeps the old one. A thread that changes the workflow updates this file before it finishes — "i don't need to explain each time my decisions when i change the workflow".

## Objective

- The measure is how often the user merges a PR as delivered, without further iterations — "the most important metric is how often would i merge a pr directly without further iterations".
- The user plans with the agent, then the agent works unattended to a ready PR — "I plan and then the agent do its things until the pr is ready, I don't care how". The user authorizes the result, not the process: research, experiments, and reversible choices need no approval.
- Planning exists to give the agent everything it cannot know, in the form that serves it best, not to extract what exploring or the skills already hold. It ends in a Done-when list: fixed lines (check, review, proof, clean diff, pipeline) plus the task's lines from planning — "the planning need to kinda be a guidated procedure that give the model all the informations that it need to do the best job possible".
- Tokens are saved by improving the workflow (less friction, recurring issues fixed), never by handing the user thinking or work the agent can do — "the token saving should be from us optimizing the workflow, removing friction, fixing recurring issues, ... and not just delegating thinking and work that you can just do yourself to me"; "i feel like the agent still consider me like one of it's agents that can call at each time to delegate thinking and work to".
- Cost is subscription quota per merged PR (Claude Max 20x, Codex 5x): a stronger model that merges in one pass beats a cheaper one that needs follow-ups — "i perfer using astra on high rather than luna low if astra can merge in a single pass".

## How to change the workflow

- Native harnesses, tuned per model: the workflow runs each model in the harness it was trained in (Opus 5.5 in Claude Code, GPT-6 in Codex), with its own text — "we aren't building a generic harness but our worfklow is using the native harness for the models in witch the agents are treined on"; "similar dx witch doesn't mean equal prompts". Only Claude Code and Codex.
- Never teach a harness its own tools or behavior its training already covers — "you keep teaching the harness how to use their tools and features witch is wired considering that they are trained on them". State the destination, the user's taste, and facts the model cannot know; what a setting can enforce goes in the setting — "why don't you just disable those tools?". Both vendors say the same: Opus 5 verifies its own work unprompted and over-verifies when told to; lean GPT prompts scored 10–15% higher with 41–66% fewer tokens (`~/.deslop/measure/2026-09-30/research-vendors.md`).
- Prompts and config only: no hooks, gates, generators, or scripts — "they seems stupid and overcomplicated, fix the prompts since the models should be good enough already". Hooks and generators were built and removed three times.
- Resolve issues up front instead of adding branches for every case — "the whole workflow need to be optimized around resolving the issues up-front and not having tons of branches to handle every possible case".
- Fix root causes at their source: a rejected rule is edited or deleted where it lives, never countered by a new one — "you should clean up and solve the root cause".
- Change on evidence: every change is A/B-tested on the replay bench with at least 3 runs per arm, since one run per arm cannot separate prompt effects from noise (the 09-30 overnight rounds did exactly that and were overfitting); iterate quickly to find issues, then fix them — "perfer quick iterations to find issues and then solve them". No word cap — "i don't want to have a word cap".
- Before calling workflow work done, ask whether the data supports the conclusion and whether the objective is met; stopping because the literal instruction ran out is the failure the user saw overnight on 09-30 — "these are a couple of questions that the agent should have asked itself before saying that it finish or stopped".
- Evals never touch a remote: no commits, pushes, remote branches, MRs, or destructive operations from any test run — "this is extremely important since i can't just commit on the repo remote just to do tests". Eval copies have no remote, pushes rewritten to an invalid scheme, and invalid forge tokens.
- dual is read-only for workflow work — "Don't do any change to dual"; it is a source of patterns only.
- Install with `node tools/workflow/src/install.ts` after every workflow change, without asking. It replaces every top-level entry of `agents/claude` in `~/.claude` and of `agents/codex` in `~/.codex`, and each skill in both `skills/` folders; `CLAUDE_CONFIG_DIR` and `CODEX_HOME` select scratch homes. It never deletes entries dropped from the source; remove those from the homes by hand.

## Planning and questions

- Planning is the default for every task, never a mode the user switches on — "i don't want to add something like discuss/plan/... it should be the default"; the harness plan mode is denied — "I hate the harness plan mode".
- Reach the user's design unprompted from their stated constraints: in thread e5836cbf the user still had to propose the versioned layout, a generic CLI, and fewer abstractions — "it still required me to be more explicit on what i wanted instead of the agent doing it himeself right away". Earlier threads on the branch and the threads, tickets, and PRs a request names are read for the user's quoted decisions; ideas and tentative remarks are confirmed, not assumed.
- Decide by trying, not by asking: the agent builds or runs every serious option, compares them on evidence, and picks the best; it never asks the user to choose between options it has not tried or to pick what to try — "the objective is trying multiple things and pick the best and not make me make assumptions on witch one i think it's best and then try only that". In thread 40ce96ee the agent asked which lookup-table model and which tracer-bullet journey to use; the user answered "idk" and "we can test all tree".
- Open-ended and unclear tickets are a first-class case, and brainstorming must be adversarial — "i will start working more and more on these open-ended and unclear tickets … i always felt that the braisntorming aspect is not good or adversarial enough": frame the problem and challenge its premise (the user's ideas included) before solutions, generate directions that differ in kind including how established products outside the repository solve it, try them, and have a fresh `review` refute the pick, since self-critique stays anchored (Every's compound-engineering ce-brainstorm and ce-ideate are the source, without their spec files, gates, or one-question turns).
- Verify instead of assuming: experiments and prototypes answer "does this work" in planning and implementation alike — "the prototyping should be a really flexible tool that you must take advantage of … The objective is not making assumptions and try stuffs". Tracer bullets, the thinnest real slice on one case, are the alignment surface — "keeping me in the loop at the start is cheap, putting me inside later is extremely more expensive".
- Build the mechanism and names the user gives; another approach is a question with its tradeoff. Push back on weak ideas with evidence — "instead of assecondating me".
- Questions go only through the question tool (`AskUserQuestion`, `request_user_input`), in one round once every question has its evidence and independent work is done — "the questions are blocking and require my focus … so I don't constantly need to switch"; never as questions or unresolved points in a reply — "i just want to align myself trough the questions". Each option shows concrete behavior and evidence; the message just before shows each option's bad and good code, media, and links, since t3 drops question previews. A custom answer signals misread intent — "I just want to feel that me and the agent are aligned". Questions are written to be answered without asking back: plain words, a concrete example and evidence per option, no label the user hasn't seen; an unsure answer ("idk", "what do you mean") means the question was unclear, so the agent clarifies and asks again, never acting on it — "it should write clearer questions in the first place, but in general always clarify and re-ask" (93 hesitations in the t3 history: 35 unclear wording, 17 missing data).
- Scratch is deleted the moment its question is settled, not at task end — "as soon as you finish a prototype and you don't need it anymore delete it, don't wait for the task to finish". On 09-30 the disk filled to 100% and t3 crashed: replays ran the workbench repository's `clone-source-repos` (vscode and others) and copied worktrees with them (~70 GB), and finished threads had left 17 GB of experiments in `node_modules/.cache/deslop` and `~/.deslop/<worktree>/`. The replay harness now blocks network clones in the fake home, refuses to start under 25 GB free, and deletes each run's home once judged.
- Prototypes run in the pair's worktree while the pair is not editing it; otherwise in a detached `git worktree add` with the pair's diff applied and a fresh install, never a `cp`/`rsync` copy — "is creating all these worktrees for the prototypes actually necessary? … given the storage we have it's not really a good option". Measured 09-30: a dual worktree costs 114 MB checkout plus 272 MB install (hardlinked; 2.3 GB apparent, what a copy would cost), a deslop one 2 MB plus 316 MB.
- Repetitive work is delegated, taste stays with the pair — "The main is usually a better agent with more 'taste', the subagents should focus more on consistent results on well scoped and well defined tasks": the pair writes the first instance, parallel `general-purpose`/`worker` agents replicate it one instance each, touching only that instance's files (installs, lockfiles, shared registries stay with the pair; 8692ef14's agents collided on bun.lock), and the pair reads every diff.
- Additions with their evidence: no wake-ups for work that notifies (8692ef14: four `ScheduleWakeup` calls while agents would notify, each followed by a repeated status table); engineering "Say each thing once" (72d758eb: the same SandboxGone mapping three times, header lowercasing twice in 8692ef14); prototypes the user reads or the pair builds on follow the engineering skill (40ce96ee: comments, swallowed errors, `throw new Error` in prototype code the user reviewed); workers add no lint suppressions (8692ef14: five identical `oxlint-disable` lines in a replicated test); `Explore` scratch never in /tmp (8692ef14: `/tmp/um.sh`); media a message embeds lives in `node_modules/.cache/deslop/proof/`, which maintenance keeps with `done-when.md`.
- The pair texts use a bold leading word per rule, grouped under replies, planning, delivery, and working — "Trim and use leading words, better structure and organize/prompt the workflow" (09-30). Rules added from the 09-30 running threads: every user message, queued ones included, fully answered (40ce96ee missed queued questions); a mark stands alone; the status table only for waiting turns and status questions (40ce96ee sent 12 tables); the Done-when list written to `node_modules/.cache/deslop/done-when.md` (8692ef14 kept it in thinking); never ask what the user delegated (8692ef14 asked which groups after "start implementing from the most important"); a card never points to an example the message doesn't show; edits with the Edit tool in minimal hunks (40ce96ee: 83 shell edits against 1 Edit); reuse the nearest implementation; a mid-task instruction done completely (quickjs left half-removed); no wake-ups for work that notifies; no `pkill`; `Explore` does web research; `review` runs no full check (it doubled the suite in 72d758eb).
- Output around questions is minimal — "i want as few output as possible and i want to focus on having good question. i don't want to read both the output text and the questions": each question card carries its own context; the message before the cards holds only each option's example (code, screenshot, link) — user's choice "Only per-option examples"; what the agent can fix or decide itself is fixed silently and never reported before delivery ("Fix silently"); a turn answering the user's question or recap request holds only that answer, and questions come in a later round ("Recap only, questions later"). In 40ce96ee an 8k-character recap before five cards drew answers about the recap and "look at the previous question response".
- Never asked: whether to refactor touched code (it follows the engineering skill) — "you still ask useless questions like if the code you are touchinng should be refactored"; what goes in this PR, what comes first, or what waits for later: everything planned goes into the current PR, organized as suits the agent — "it ask witch one should it do first instead of just just doing them"; "if we discussed something just do it in the current pr, if i need multiple prs i will split them later … i shouldn't be in the loop anyway so it doesn't matter witch is done first". Always asked: scope beyond the request (upgrades, CI, images, neighbouring features, agent docs) — "scope expansions aren't allowed and require questions"; removing a feature or service.
- The user is rarely away during planning, so there is no away mode — "it's rare that i'm away during planning so don't even consier it".
- No plans shown and no spec or ticket files the user must write or read; decisions stay in the conversation, and the only file is the agent-private `node_modules/.cache/deslop/done-when.md` — "it's useless to output the plan"; "I don't want to need to write tickets/specs to files like the Matt skills". Nothing the workflow fixes is shown either — its steps, fixed checks, or the Done-when list — since the user built the workflow and knows them: "there is no point in showing to the user fixed infromations or fixed instructions".
- Replanning is a full planning round: a steer that changes the approach, design, or scope reruns planning and rebuilds the branch as one clean pass — "it should be like planning again with prototype and everything … while cleaning up the code of the previous implementation".

## Delivery

- Commits happen at delivery only, once everything is checked, reviewed, and proven: no commits while working (user's answer, 09-30). The default branch is protected by deny rules; the PR stays a draft, and every push rewrites its title, body, and changesets to the whole branch's net change, written by the reply rules: what changed and why, visual, no introduction or recap, nothing the reader already knows — "changelogs keep stacking on each new iteration instead of reflect only what the pr changed"; "the pr body and stuffs like that should follow the same instructions of the output". The default branch is merged in before the final check and review; the pipeline must be green.
- Delivered work is already clean, simplified, and improved: nothing the user would predictably ask next — "i'm tried of me needing to constantly ask to simplify/cleanup/improve … give me something that is already perect"; never a "simplified on a second round".
- Proof is mandatory: screenshots and a short H.264 `.mp4` from agent-browser through the existing UI, before and after — "the videos and images proofs are mandatory"; t3's preview and device tools are denied (headless host). Instructions shipped for agents are proven by a fresh agent on a real task.
- Cleanup is aggressive: anything a change leaves unused, replaces, or makes useless is removed in the same change, whatever its kind — "also include configs, validations, code branches, tests, docs, … anything that is superseded" — while adding anything unrequested is "extremely bad" — "if you change some code and that code make something unused just remove it. Always cleanup aggressively unused codes, useless branches" (09-30, superseding the workbench replay's "keep them even if fallow flag them"). A check that conflicts with something the user asked to keep is satisfied another way, never suppressed.
- A problem the agent cannot solve goes to the user, never a workaround — "if you can't solve the problem or don't know how don't find workaround and ask the user". A reported problem names a class: every instance in scope is fixed.
- Everything that can run in the background does, as non-blocking as possible — "if something can be done in the background it should, be as non blocking as possible when it make sense". The Claude pair runs the pipeline watch itself as a background command so t3 shows "Monitoring" (t3 shows it only when no agent is live and a background Bash or `Monitor` task runs; a foreground or agent-run watch shows "Working"), and hands only a failure to `general-purpose`.
- Superseded work stops at once; a revision known to be broken is never reviewed, pushed, or watched — "If you already know that something is superseded, not accurate, or that you will discard the result anyway interrupt/stop doing it".
- Mid-task messages that don't change the task run alongside it, marked or not — "usually I say 'as a side note' … probably it's not even needed".
- The user is out of the loop after planning — "staying inside the loop is the most frustrating part".

## Replies

- t3 shows only each turn's last message; everything earlier folds into a "Worked for …" row. That message holds only what is new: answers, findings, embedded media, and links t3 cannot show; no PR, commit, pipeline, or agent information t3 already shows, apart from the status table below — "anything that can be shown by t3code shouldn't stay in the output".
- Technical and schematic, outcome first, with no introduction, closing, summary, or recap: the first line is the first new fact — "remove introduction and ending, recaps, and in general make more technical and schematic"; "You still add intro/outro/summaries to the output, be more cocise and only show informations that can be userful to the user". Never a mark and words that say the same thing — "Don't have icons/emoji and text that say the same thing". Emoji marks stay: the user tried ASCII marks and went back — "Maybe the emoji was better and easier to understand".
- Show instead of describing, using Markdown fully: screenshots and MP4s for anything visible, tables, code and diff blocks, file trees — "For me it's extremely important to use visual representation and take full advantage of markdown"; "I was also talking about images and videos". A minimal bad/good code block for every change, proposal, and rejected candidate — "i don't see enough minimal code example".
- Each fact once, in one form, and tables only with the columns the reader needs — "never have multiple representation or instances of the same information in the same output".
- Plain words: no abbreviation, name, or label the user hasn't seen — "Can we stop using useless abbreviations?" (after replay tasks were called P3 and F1).
- No Mermaid; t3 does not render it.
- One callback beats many: a turn that only waits, and the answer to a status question, is a lean status table (Step | State: ✅ done, ⏳ running, ⏸️ waiting, with no text on what a step waits for — "it's a useless information I just want to how that it's waiting for something"; the user picked this shape from the 09-24 manual-run-button thread e9c3c64c), never silent since Claude Code re-prompts silent turns; phase changes show no other way (the todo/plan tools stay off in both harnesses: "no, don't enable them"), and progress is one line mid-turn at a phase change — "i honestly would prefer to be called back after [ten] minutes 1 time rather than being called back for unrelated things 5 times every 2 minutes".
- No time units in prompts; the agent has no sense of elapsed time — "the agent doesn't really have a concept of time so don't put time".

## Code quality

- Code quality is the top priority, reached on the first pass through the engineering skill, then lint with autofixes — "im not looking for code that it's just good enough". The engineering skill is the only home of cross-repository rules and wins over a repository's CODING_STANDARDS.md; one-repository rules go in that repository's CODING_STANDARDS.md (deslop's schema/service/utils layout lives there, not in the skill).
- Understood at first glance, for everything — "the code doesn't need to be clever it need to be simple". File organization: consistent role folders like a file-based router, explicit names, bigger files over nearly empty ones, no barrels, `package.json` `exports` and `imports` aliases mandatory, tests beside their subject — "if i use a file tree i should be able to quickly find everything at first glance".
- Do only what is asked and never add anything unrequested; composable Effect building blocks, never wrappers like `serve(app)` — "i'm just providing them and composing them like normal effect modules and not just wrapping everything".
- Tests guard only logic worth guarding, at the seam, as a black box — "I would prefer a 10% coverage that is extremely well curated". One way to do each thing and no compatibility layers — "don't consider backward and forward compatibility since they don't matter". Type inference first. Idiomatic, documented Effect from `~/.deslop/repos/effect` wins over house conventions, except standalone `pipe` and `return yield* E.make(...)`; flatness outranks idiom. Schema.Class and module-level `ManagedRuntime.make` are banned; readonly only on service shapes and class members; tests use `assert` from @effect/vitest.
- Lint rules are validated on real deslop and dual code before they ship, narrow rules with real hits over catalogs; the skill and static analysis stay in sync, and the toolchain stays at the latest compatible versions via the root `upgrade` script — "update everything to the latest version that ensure compatibility between the deps". Lint runs once per finished unit, never per edit.
- Colleagues use Matt Pocock's documents (CONTEXT.md, `docs/adr/`, CODING_STANDARDS.md, `docs/agents/*.md`), so the workflow follows them instead of special conventions.

## Harness facts

- t3 owns worktrees, branches, diff review, and PR linking, and sets the pair's model per thread. It launches Claude with `--setting-sources=user,project,local`; a user output style reaches the main thread only, and roles receive the repository AGENTS.md.
- t3 renders images and videos embedded by absolute path (`~/.deslop/repos/t3code/apps/web/src/components/ChatMarkdown.tsx`) and keeps only each question option's label and description (`apps/server/src/provider/Layers/ClaudeAdapter.ts:4462-4467`). It has no GitLab media proxy, so MR uploads do not load off-VPN; chat media is enough.
- Claude threads reload the pair text when the composer's model or effort changes or after 30 idle minutes; a continued Codex thread picks up new developer instructions at its next compaction. Role files are read at each spawn.
- Prompt caches: Claude main thread 1 hour, Claude subagents 5 minutes unless `experimental.cacheTtl: 1h` (`general-purpose` sets it), GPT-6 30 minutes. `BASH_MAX_TIMEOUT_MS=3000000` keeps Claude's waits inside the hour; Codex's `background_terminal_max_timeout` and `default_wait_timeout_ms` are 1,500,000 ms.
- Claude Code injects "The user hasn't heard from you in a while" after silent turns in t3's stream-json sessions; `CLAUDE_CODE_SILENT_TURN_REMINDER=0` disables it. `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=1` stops nested spawns.
- Claude Code re-prompts a turn that ends with no visible text ("[Your previous response had no visible output…]", changelog: "Claude now re-prompts once"; seen in e5836cbf at L4833, L5037, L6490, L8914 and in this workflow's own thread). It is a different mechanism from the "hasn't heard from you" reminder that `CLAUDE_CODE_SILENT_TURN_REMINDER=0` turns off, so a waiting turn is never silent. On 09-30 a rerun on 2.1.283 found 0 of 6 invented completion notices with background agents (`~/.deslop/measure/2026-09-30/wait-exp/`), where 09-28 had found 2 of 3.
- Codex multi-agent v2: a spawn forks the whole history unless it passes `fork_turns: "none"`; a finished agent's result reaches the pair only through `wait_agent` or the user's next message; open agents count toward a thread limit of 6 until `close_agent`; role developer instructions replace the root's, and nothing stops a role from spawning. - gpt-6-astra receives "Do not spawn sub-agents unless … explicitly ask"; `[features.multi_agent_v2] multi_agent_mode_hint_text` replaces it. Codex's `request_user_input` needs `default_mode_request_user_input` outside Plan mode. Codex keeps its default personality; `personality = "none"` stripped its base instructions. - Quota per run: Codex rollouts carry `rate_limits` in `token_count` events; Claude's stream-json emits `rate_limit_event` with five-hour and seven-day utilization.
