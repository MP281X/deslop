# Workflow

This file is the workflow's memory, written for the agent that changes it: the current decisions with the user's reasons, the facts they rest on, and where the evidence is. It holds the current state only. When a decision changes, rewrite its line in place with the new reason; git history keeps the old one. A thread that changes the workflow updates this file before it finishes — "i don't need to explain each time my decisions when i change the workflow".

## Objective

- Success includes merge-as-delivered quality, fast useful iterations, and low attention/context-switch cost — "increase my satisfaction ... improving the quality and speed and token efficiency"; "the context switch is already making me go crazy". Remove observed overhead at its source throughout the work, not just prototype setup — "whatever is making you slow must be optimized" (10-03). A shorter response or cheaper model is not an improvement if it hides a failure or needs another correction. Single small evals establish their behaviors, not a satisfaction or speed gain.
- The user works from rough intent in one long thread per feature/worktree, steering when ideas arrive; there is no frozen-ticket planning/build handoff — "requirements aren't clear ... exploration, prototypes, trial and error"; "extremely quick iterations instead of a normal planning and questioning". The agent owns research, trials, reversible technical choices and scheduling, continuing unattended without asking the user to orchestrate.
- Discovery gets the next useful working example and settles what only the user can know, not what tools or skills can answer. The private Done-when list exists from the first example and tracks current criteria, observations and unresolved questions; it evolves rather than freezing a specification. Final check, review, proof and clean net diff remain required.
- Tokens are saved by improving the workflow (less friction, recurring issues fixed), never by handing the user thinking or work the agent can do — "the token saving should be from us optimizing the workflow, removing friction, fixing recurring issues, ... and not just delegating thinking and work that you can just do yourself to me"; "i feel like the agent still consider me like one of it's agents that can call at each time to delegate thinking and work to".
- Cost is subscription quota per merged PR (Claude Max 20x, Codex 5x): a stronger model that merges in one pass beats a cheaper one that needs follow-ups — "i perfer using astra on high rather than luna low if astra can merge in a single pass".

## How to change the workflow

- The workflow is optimized for the happy path only — "In precisions conversations I added conditionals over some parts of the workflow (e.g. don't commit, just plan, …) but we shouldn't consider them in the workflow": no rule for one-off conditionals, and replays score none of them. The rest of the host is read-only for a thread — "Don't touch dual, in general we should say something to treat the rest of the system as read only when working on a repo".
- Native harnesses, tuned per model: the workflow runs each model in its native harness (Opus 5.5 in Claude Code, GPT-6 in Codex), with its own text — "similar dx witch doesn't mean equal prompts". Other products inform experiments and specialist patterns, not an untested replacement harness. The 10-02 round permits researching Amp, Factory and cross-model cooperation but forbids Claude execution for now to preserve its quota.
- The workflow owns the whole system prompt in both harnesses instead of countering their defaults — "if the instruction say x we can't just say to do y and never x"; Claude: "if we can fully wrplace it it would be better"; Codex: "can't we override part of those? because those defaults are honestly kinda terrible". The replacements keep the default lines worth keeping (Claude Code's harness, security, and authorization lines; Codex's autonomy, steering, link formatting, and exec guidance) and drop the ones that contradict the user (comment density, not narrating rejected options, prose answers, Mermaid, 60-second updates and waits, `request_user_input_async`). Never teach a harness its own tools: state the destination, the user's taste, and facts the model cannot know; what a setting can enforce goes in the setting — "why don't you just disable those tools?". Both vendors say the same: Opus 5 verifies its own work unprompted and over-verifies when told to; lean GPT prompts scored 10–15% higher with 41–66% fewer tokens (`~/.deslop/measure/2026-09-30/research-vendors.md`).
- Prompts and config only: no hooks, gates, generators, or scripts — "they seems stupid and overcomplicated, fix the prompts since the models should be good enough already". Hooks and generators were built and removed three times.
- Resolve issues up front instead of adding branches for every case — "the whole workflow need to be optimized around resolving the issues up-front and not having tons of branches to handle every possible case".
- Fix root causes at their source: a rejected rule is edited or deleted where it lives, never countered by a new one — "you should clean up and solve the root cause".
- Change on evidence, with small tests that check exactly what a change needs (a captured request, a few bare prompts, lint over the examples, one targeted replay), never large eval rounds — "prefer smaller tests to check what you need and not big tests that add no value" (10-01, after the 09-30 rounds spent most of a week's quota). No word cap — "i don't want to have a word cap". Happy path everywhere, commands and scripts included, for this one machine — "if something is not in the happy path the agent is smart enough to find a solution anyway"; "i only use this machine".
- Before calling workflow work done, ask whether the data supports the conclusion and whether the objective is met; stopping because the literal instruction ran out is the failure the user saw overnight on 09-30 — "these are a couple of questions that the agent should have asked itself before saying that it finish or stopped".
- Evals never touch a remote: no commits, pushes, remote branches, MRs, or destructive operations from any test run — "this is extremely important since i can't just commit on the repo remote just to do tests". Eval copies have no remote, pushes rewritten to an invalid scheme, and invalid forge tokens.
- dual is read-only for workflow work — "Don't do any change to dual"; it is a source of patterns only.
- Install with `node tools/workflow/src/install.ts` after every workflow change, without asking. It replaces every top-level entry of `agents/claude` in `~/.claude` and of `agents/codex` in `~/.codex`, and each skill in both `skills/` folders; `CLAUDE_CONFIG_DIR` and `CODEX_HOME` select scratch homes. It never deletes entries dropped from the source; remove those from the homes by hand.

## Discovery and questions

- Exploration, brainstorming, useful visual proof, independent background work and incorporation of side notes are inferred from intent/state, never triggered by special words — "the workflow doesn't need my constant usage of leading words". Depth follows uncertainty; neither a complete survey nor every background result blocks the next useful trial. The harness plan mode remains denied — "I hate the harness plan mode".
- Reach the user's design unprompted from their stated constraints: in thread e5836cbf the user still had to propose the versioned layout, a generic CLI, and fewer abstractions — "it still required me to be more explicit on what i wanted instead of the agent doing it himeself right away". Earlier threads on the branch and the threads, tickets, and PRs a request names are read for the user's quoted decisions; ideas and tentative remarks are confirmed, not assumed.
- Decide by trying: contrasting serious contenders get small real experiments; a focused test can eliminate a weak direction without a full build. Select reversible technical choices on observed tradeoffs and the user's standards, not a user architecture election. In 40ce96ee abstract lookup-table cards produced "idk" and "we can test all tree"; the 10-02 correction asks for fast comparisons rather than a compulsory build of every conceivable direction.
- UI prototyping has no fixed three-variant quota: compare serious alternatives with the smallest real slice that settles the uncertainty, then remove losing variants. This replaces the design skill’s mandatory full variants under the 10-02 quick-iteration preference.
- Open-ended work is the normal case. Challenge the premise, search directions that differ in kind and borrow established product mechanisms; ambition is better outcomes, not more code or unauthorized scope. Fresh review challenges consequential/hard-to-reverse designs alongside independent work, not every small iteration; final whole-diff review stays mandatory. Amp/Factory's bounded specialists fit this better than a standing committee or factory ticket pipeline.
- Verify instead of assuming: experiments and prototypes answer "does this work" in planning and implementation alike — "the prototyping should be a really flexible tool that you must take advantage of … The objective is not making assumptions and try stuffs". Tracer bullets, the thinnest real slice on one case, are the alignment surface — "keeping me in the loop at the start is cheap, putting me inside later is extremely more expensive".
- Respect explicit requirements and names, but tentative implementation ideas are hypotheses to investigate, not approvals. Push back with a tried alternative — "instead of assecondating me". Reversible technical details are the agent's job; changing an agreed requirement remains a user-owned decision.
- Questions go only through `AskUserQuestion` or `request_user_input`, batched once their evidence is ready, only for genuine user-owned uncertainty — "the questions are blocking and require my focus". Do not join unrelated background work first or ask the user which technical experiment to run. Each card stands alone in plain words with a concrete example and evidence; the preceding message holds only the needed artifacts because t3 drops previews. A custom answer revises the misread part, preserving agreed decisions; "idk"/"what do you mean" requires clarification, not guessed consent (93 historical hesitations: 35 unclear wording, 17 missing data).
- The user prompts with the bare request — "The objective is for me to prompt in the most stupid way possible". A 09-30 count of 1,388 user messages found the steering they still type: simplest code (138), discuss/plan/brainstorm (135), cleanup (110), prototype/try (101), "anything else to improve?" (101), status pings (91), analyze previous threads (75). Deslop-only taste lives in its CODING_STANDARDS.md — "Some of the taste you are talking about is specific to this repo".

- Mid-task messages that don't change the task run alongside it, marked or not — "usually I say 'as a side note' … probably it's not even needed".
- The agent keeps moving without user scheduling or repeated approvals; the user can steer whenever an idea arrives — "staying inside the loop is the most frustrating part". Canonical current criteria and observations are rewritten before handoff/compaction, not buried in an append-only log.

## Replies

- t3 shows only each turn's last message; everything earlier folds into a "Worked for …" row. That message holds only what is new: answers, findings, embedded media, and links t3 cannot show; no PR, commit, pipeline, or agent information t3 already shows, apart from the status table below — "anything that can be shown by t3code shouldn't stay in the output".
- Technical and schematic, outcome first, with no introduction, closing, summary, or recap: the first line is the first new fact — "remove introduction and ending, recaps, and in general make more technical and schematic"; "You still add intro/outro/summaries to the output, be more cocise and only show informations that can be userful to the user". Never a mark and words that say the same thing — "Don't have icons/emoji and text that say the same thing". Emoji marks stay: the user tried ASCII marks and went back — "Maybe the emoji was better and easier to understand".
- Show useful execution evidence rather than describing it: meaningful images/video, compact comparisons, code when its difference needs reading, a tree when structure matters. The 10-02 request to minimize cognitive load replaces compulsory bad/good blocks for every rejected candidate. Show a result, consequential difference, actionable blocker or user-owned decision; hide internal scheduling and routine progress. Discussion stays in the conversation, not new analysis reports, diagrams or recap files — "Can you stop generating those artifacts/files?". Existing private task state and required execution evidence are not extra deliverables.
- Each fact once, in one form, and tables only with the columns the reader needs — "never have multiple representation or instances of the same information in the same output".
- Plain words: no abbreviation, name, or label the user hasn't seen — "Can we stop using useless abbreviations?" (after replay tasks were called P3 and F1).
- No Mermaid; t3 does not render it.
- One callback beats many: a turn that only waits, and the answer to a status question, is a lean status table (Step | State: ✅ done, ⏳ running, ⏸️ waiting, with no text on what a step waits for — "it's a useless information I just want to how that it's waiting for something"; the user picked this shape from the 09-24 manual-run-button thread e9c3c64c), never silent since Claude Code re-prompts silent turns; phase changes show no other way (the todo/plan tools stay off in both harnesses: "no, don't enable them"), and progress is one line mid-turn at a phase change — "i honestly would prefer to be called back after [ten] minutes 1 time rather than being called back for unrelated things 5 times every 2 minutes".
- No time units in prompts; the agent has no sense of elapsed time — "the agent doesn't really have a concept of time so don't put time".

## Code quality

- Code quality is the top priority, reached on the first pass through the engineering skill, then lint with autofixes — "im not looking for code that it's just good enough". The engineering skill is the only home of cross-repository rules and wins over a repository's CODING_STANDARDS.md; one-repository rules go in that repository's CODING_STANDARDS.md (deslop's schema/service/utils layout lives there, not in the skill). The skills never depend on a deslop clone or name deslop as the bar — "it shouldn't work only if i have the repo cloned"; they name only the published `@deslop/workflow` preset.
- Understood at first glance, for everything — "the code doesn't need to be clever it need to be simple". File organization: consistent role folders like a file-based router, explicit names, bigger files over nearly empty ones, no barrels, `package.json` `exports` and `imports` aliases mandatory, tests beside their subject — "if i use a file tree i should be able to quickly find everything at first glance".
- Do only what is asked and never add anything unrequested; composable Effect building blocks, never wrappers like `serve(app)` — "i'm just providing them and composing them like normal effect modules and not just wrapping everything".
- Tests guard only logic worth guarding, at the seam, as a black box — "I would prefer a 10% coverage that is extremely well curated". One way to do each thing and no compatibility layers — "don't consider backward and forward compatibility since they don't matter". Type inference first. Idiomatic, documented Effect from the installed `node_modules/effect/src` wins over house conventions, except standalone `pipe` and `return yield* E.make(...)`; flatness outranks idiom. Schema.Class and module-level `ManagedRuntime.make` are banned; readonly only on service shapes and class members; tests use `assert` from @effect/vitest.
- Lint rules are validated on real deslop and dual code before they ship, narrow rules with real hits over catalogs; the toolchain stays at the latest compatible versions via the root `upgrade` script — "update everything to the latest version that ensure compatibility between the deps". Lint runs once per finished unit, never per edit. The engineering skill and lint are one pair — "the skill should make the agent write extremely good code that pass the linting on the first pass, the linter should mostly be a fallback ... complement the linting to not make so it keep looping": every good example passes lint and format as written (checked 10-01 by linting each block), the forms lint enforces without an autofix come first with the single form that satisfies every rule involved (fallback `??`, flat statements, handlers, tuples, failures in generators, casts, decoders), and lint messages name their replacement.
