# Retrospective

Optimize delivery time at unchanged accepted scope and quality. Corrections, escaped defects and rework are outcomes; token volume, calls and gate counts are diagnostics, not targets.

- **History.** Read named threads with T3's thread tools, including other workers and children; environment's Maintenance has the recipe. For a broader audit, inventory since the last merged retrospective. Recover the instructions active then; separate actual user messages from generated wakes.
- Tie each proposed change to a demonstrated failure or explicit user choice. Distinguish a missing rule from an ignored rule, a tool defect or a limitation already fixed. Use the installed version's source or a deciding probe for tool claims.
- Keep local facts, user choices and corrections the model cannot reliably infer. Remove duplication, default behavior and obsolete workarounds.
- Read the affected instruction history before reversing it. Preserve deliberate safety and quality boundaries; earlier rejections stand unless new evidence addresses their reason.
- Rewrite the existing owner, not another layer: lint for mechanical forms, repository documents for contracts and taste, skills for judgment, provider prompts/settings for harness behavior, environment for infrastructure.
- **Threshold.** A repeated failure or explicit user choice earns an instruction; one slip under a clear rule does not.
- **Conflict.** Replace the losing rule instead of adding an exception. Skill descriptions name observable load triggers, not just topics.
- Validate uncertain removals on representative tasks. Compare the same input and preserve the protected outcome; fewer bytes or checks alone prove nothing.

Present the minimal replacement and its boundary before implementing an unapproved direction. For each removed behavior, name its remaining owner or say it is being dropped. Publish authorized changes per pull-requests; corrections in the retrospective's own thread belong in the same PR.
